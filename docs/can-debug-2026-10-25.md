# CAN transmit blockage investigation — 2026-10-25

Motor power was confirmed on. No controller was running. All probes transmitted
only state requests (type 2) and fault-register reads (type 9, 0x3022); no enable,
control, stop, zero, or motor parameter write was sent during this investigation.
All received state replies reported disabled.

## Reproduction and isolation

An initial single request to each of 12 and 13 immediately failed with ENOBUFS.
The kernel transmit queue contained 11 pending frames, despite no active sender.
Taking can1 down/up recovered transmission. Low-rate production inventory
polling then reproduced the blockage in approximately 3 seconds while disabled.
This establishes that actuation is not required for the failure.

Raw SocketCAN probes included local transmit-completion echoes as well as motor
replies, allowing queued requests to be distinguished from completed sends.

During the leg 5 probe, 51 answered only 8/39 state requests and 5/39 fault reads.
Every request to the other four motors received a reply. The state replies from
51 reported mode 0, no state faults, position -0.68188754 rad and temperature
28.6 C; received fault-register values were zero. The observations do not reveal
an obvious second encoder position or prove/exclude duplicate IDs.

## Interpretation

Adding traffic to ID 51 is a reproducible trigger in this setup. A simple lack of
motor power or generic request-rate overload does not explain these comparisons.
The physical cause is still unknown: ID 51's node/connection, duplicate address,
CAN signal integrity, or adapter/firmware handling of that traffic remain possible.
The mapping identifies 51 as leg 5 yaw; physical identity was not reverified.
Zero reported bus-error counters are not proof that the physical bus is sound.

The adapter is a canable2 gs_usb, USB serial 0035005C4633500E20303035, connected
at 4-2. Kernel/driver: 6.8.0-1048-raspi. Its descriptors do not expose a firmware
commit/version. No firmware update or motor ID change was attempted.

## Software isolation

The leg 1 profile previously selected actuation IDs 12/13 but still polled all
nine can1 motors, including 51. `telemetry_motor_ids` now explicitly restricts
transport driver creation and polling to configured IDs; the leg 1 profile sets
`[12, 13]`. Full-inventory polling remains the default on configured buses for
other profiles. Unpolled motors remain unknown, not reported healthy or ready.
This avoids the identified request pattern during leg 1 work; it does not repair
or physically isolate the wider CAN bus. A faulty node can still disrupt a bus
without being polled. Homing remains opt-in and disabled in the checked-in profile.

Next physical investigation: verify ID 51's power/CAN connections and unique
address, then repeat the omitted/reintroduced-node comparison with that physical
node isolated while preserving CAN termination. Power off before changing wiring.

Evidence is in `log/can-debug-20261025/`. Read-only probe programs were kept in
`/tmp`; no extra runtime modules were added to the package.


The updated production transport with `motor_ids=[12,13]` passed 15 seconds of
idle polling and 60 seconds at the priority homing rate, with both drives disabled.
Maximum observed state/fault ages during priority polling were 0.0462 s for 12
and 0.0519 s for 13, below the unchanged 0.25 s limit. There were no transport
errors or reported motor faults. Thirty-nine offline tests pass and low-level/
bringup packages build successfully. All diagnostic polling was stopped at the
end; no motion controller or homing run was started.

finite telemetry and no reported faults. No CAN transmit errors occurred.
No actuation or motion test was performed, and the probe was closed afterward.
